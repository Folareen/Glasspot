Double-entry ledger, ledger is the only source of truth. Every money movement writes two rows — debit one account, credit another — and they sum to zero. Balance is always derived from SUM(entries); a materialized balance table is allowed as a read cache only if it's written in the same DB transaction as the ledger entries that produced it (under the same row lock), stays reconstructable from the ledger at any time, and is never mutated independently of a ledger posting. This alone kills the majority of money bugs (race conditions, lost updates, no audit trail) before they exist. A transaction isn't limited to exactly two entries — every contribution and every payout/refund actually posts four (pot/platform_float, platform_revenue's cut, nomba_fee_expense's cut, and nomba_clearing's matching contra-entry) to account for Nomba's real flat fee separately from the platform's own cut — see apps/backend/src/lib/fees.ts's inboundFeeLegs/outboundFeeLegs for the worked arithmetic and account roles.
Money is an integer internally, always. Kobo, not naira. Never float/double anywhere money is stored or computed — the ledger, the DB, every service/business-logic layer. Float drift is how reconciliation breaks six months in and nobody can find the missing ₦3. Field/column/variable names do NOT carry a `Kobo` suffix (e.g. `amount`, not `amountKobo`) — every money field in the DB/ledger/service layer is a kobo integer (bigint) by convention, so the suffix is redundant.

The one deliberate exception is the wire boundary: every API request/response money field is a naira string with exactly two decimal places ("100.50", "0.00"), never a kobo integer — see apps/backend/src/modules/pots/pots.schema.ts's `nairaAmount` schema. This is what the frontend sends/displays directly, with no client-side arithmetic. Conversion between the two representations happens in exactly one pair of functions, `nairaStringToKobo`/`koboToNairaString` (`apps/backend/src/lib/money.ts`, mirrored for the frontend's own simulated-ledger math in `apps/web/lib/money.ts`), called right at the wire boundary (request validation done, before touching the service layer; response about to be sent) and nowhere else. Both conversions split the string on its decimal point and parse each part as a plain integer — never `Number()`/`Math.round()` on the combined value — so the conversion is always exact, never subject to float representation error. The Nomba integration is a second, separate naira boundary (Nomba's own API is naira, not kobo) — see `apps/backend/src/integrations/nomba/nomba.client.ts`'s top-of-file UNITS comment; conversion there goes through the same two functions, never inline `/100`/`*100` math.
Never round money up, anywhere, for any reason. Every rounding/truncation point in this codebase must round down (or truncate toward zero) so the system never claims to hold, owe, or charge more than it actually does. This shows up in three distinct places: (1) integer bigint division for pro-rata splits (`pots.service.ts`'s `postContributorsRefund` — `(contributed * balance) / totalContributed` truncates toward zero by construction, deliberately leaving an uncollected remainder in the pot rather than distributing more than the balance actually holds); (2) parsing a naira float FROM an external source (Nomba's webhook `transactionAmount`, or any `nombaAmount`/reconciliation figure) into kobo — always via `.toFixed(2)` then `nairaStringToKobo`, never `Math.round(x * 100)`, since multiplying a float by 100 first can amplify a representation error into rounding up an extra kobo (`contributions.service.ts`'s `confirmFunding`, `reconciliation.service.ts`'s `nombaNairaToKobo`); (3) reshaping raw user-typed input on the frontend into the wire naira format — `toNairaAmount` (`apps/web/lib/money.ts`) truncates a too-long decimal (`"100.999"` → `"100.99"`), never rounds it up to `"101.00"`. If a new rounding point is ever needed, it must round down or reject the input outright — never round to nearest, never round up.
Ledger entries are immutable. No UPDATE on a transaction row, ever. Mistakes get corrected with a new reversing entry, not an edit. This is also just accounting — you don't erase history, you append to it.
Idempotency keys on every mutating money endpoint. Charge, payout, refund — all of them. Client generates the key, server stores result against it, retries return the cached result instead of re-executing. Non-negotiable because retries will happen (network blips, client double-taps, queue redelivery).
Webhooks are a notification, not a source of truth. They get missed, delayed, duplicated, or your server is down when they fire. Run a reconciliation job (BullMQ cron, every few minutes for pending, daily for full sweep) that polls the provider's transaction-status API for anything still "pending" past a threshold. Provider's API state wins, always — your local state is a cache of it.
Never trust a client-supplied amount for execution. Client can request, server computes/verifies against the pot's actual target and rules before any transfer call goes out. This includes the flat outbound fee: every payout/refund is charged an additional ₦50 on top of the amount the recipient receives, so the pot's balance must cover `amount + 50`, not just `amount` — enforced once, authoritatively, in `postFixedAmountDisbursement` (apps/backend/src/modules/pots/pots.service.ts), the single choke point every payout/refund path (manual, target_based, recurring, scheduled, the contributors fan-out) funnels through.
At-least-once delivery, everywhere. Webhooks, queue jobs, provider retries — assume duplicates. Every handler must be safe to run twice. (Same root fix as idempotency keys, applied system-wide.)
Lock state transitions at the DB level. Pot status (open → locked → payout_pending → settled, or → refund_pending → refunded) needs SELECT FOR UPDATE or optimistic locking on concurrent writes. With unanimous approval specifically — two members approving in the same instant must not both trigger the payout call. This is the one most likely to bite you live during demo day if skipped.
Money in flight is tagged, not just counted. Once payout is triggered or pending approval, those funds need a status that blocks a simultaneous refund request from touching the same pool. Two operations racing on the same funds is the classic double-spend bug in pooled-money products specifically.
Never blind-retry a transfer call on timeout. If a payout call to Nomba times out, you don't know if it executed. Query transaction status first; only retry if confirmed not-executed. Blind retry on timeout is how you double-pay someone.
Audit log separate from the ledger. Who approved, when, what action, what context — for dispute resolution, not for balance math. Cheap to add (one table, append-only), expensive to reconstruct after the fact if you skip it.
No silent failures. A failed transfer or refund must surface somewhere — alert, dashboard flag, anything — not just sit as a stuck row nobody notices.
Admin-triggered money movement needs a second factor, not just a valid session. Manual payout trigger and admin refund trigger both require a one-time email code first (request it, then trigger with the code) — a stolen/hijacked admin session alone shouldn't be enough to move money out. The code is bound to the exact request context (destination/amount) it was issued for, so it can't be replayed against a retry with different parameters.
